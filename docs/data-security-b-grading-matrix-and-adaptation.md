## 一、统一规则：R1–R5

定级不是"看条数"，而是"类别 → 量级 → 系统重要性 → 影响后果 → 扩散/主观恶性"五维，按 R4 就高。以下 5 条为本矩阵的唯一口径，13 节全部用它重算。

### R1 类别优先（先判类别，再判条数）

| 类别 | 判定要点 | 典型字段 |
|---|---|---|
| 核心数据 | 一旦泄露/篡改/毁损，直接危及患者生命安全或全院诊疗秩序 | HIS 计费主库、EMR 病历正文、LIS 检验结果、PACS 影像、处方与医嘱 |
| 重要数据 | 一旦出事，造成较大范围业务中断或大规模个人信息权益损害 | 门诊/住院业务库、预约挂号库、医保结算库、辅助诊断模型与训练集 |
| 一般数据（含个人信息） | 其余业务与个人信息 | 客户联系信息、运维日志、统计数据 |

**本方案的"一般 / 敏感"个人信息拆分口径**（这条是 13 节能自洽的关键，必须在评审时确认）：

- **敏感个人信息**：病历正文、诊断、检验检查结果、医学影像、生物识别（人脸/指纹）、行踪轨迹、不满十四周岁未成年人信息、身份证号。
- **一般个人信息**：姓名、手机号、住址、就诊卡号、就诊科室、费用金额、预约与挂号记录。

> 依据：《个人信息保护法》第 28 条；《数据安全法》第 21 条分类分级。医院语境下"就诊卡号 + 姓名"单独看是一般，**一旦与病历正文、诊断、检验结果同库同批出现，按敏感认定**——R4 就高。

### R2 个人信息量级分档（去重后自然人条数）

| 等级 | 一般个人信息 | 敏感个人信息 |
|---|---|---|
| Ⅰ 特别重大 | ≥ 10 万条 | ≥ 5 万条 |
| Ⅱ 重大 | 1 万 – 10 万条 | 5 千 – 5 万条 |
| Ⅲ 较大 | 1 千 – 1 万条 | 50 – 5 千条 |
| Ⅳ 一般 | < 1 千条 | < 50 条 |

- 与 F22 现有 5 档（50 以下 / 50–1000 / 1000–1 万 / 1 万–10 万 / 10 万以上）的映射：一般档直接落 F22 四档；敏感档的 50–5 千跨 F22 的"50–1000"与"1000–1 万"两档，**必须在"定级依据"里写明用的是敏感档**，否则单看 F22 量级下拉会误判。
- 边界规则：区间含下界不含上界（"5 千–5 万"含 5000、不含 50000），跨档时按 R4 就高。

### R3 非个人信息事件：按影响后果 + 业务中断范围

适用于 §4 假冒、§7 拦截、§8 投毒、§14 勒索，以及任何"计量对象不是自然人条数"的节：

| 等级 | 影响后果 | 业务中断范围 |
|---|---|---|
| Ⅰ | 患者安全事件或全院核心系统停摆 | > 4 小时且涉及急诊/手术/住院 |
| Ⅱ | 核心业务受损、基金/资金损失、监管立案 | 1–4 小时或涉及 2 个以上核心系统 |
| Ⅲ | 单一业务受损、可快速恢复 | < 1 小时或仅辅助功能停用 |
| Ⅳ | 无对外影响、可完整恢复 | 无中断或 < 30 分钟 |

> 业务中断时长以"核心业务不可用"起算，不含演练组织时间；必须在 F22 新增的"业务中断时长"字段留痕，不能只写在节点正文。

### R4 就高定级（必须写明触发维度）

量级、类别、后果、系统重要性任一维度命中更高等级，即按高等级定；但**"定级依据"必须写明是哪一维触发**，只写"按预案"视为证据不足。这解决了"条数只到Ⅲ、后果是Ⅱ"的类矛盾。

### R5 可回指（事实 → 条款 → 等级）

每个剧本的定级节点必须能三步回指：F22 字段值（事实）→ 本矩阵 R1–R4 或法定条款 → 等级结论。迁移里的 `quality_rules` 要能校验这三步都在表单里有对应输入。

#### 3.1.4 归一规则改法（最小改动，不搞乱旧 8 类）

把 `ledgerEventOf` 从"整词 → 前两字"改为**"精确 → 最长整词 → 前两字兜底"三级**：

```go
func ledgerEventOf(scenarioName string, eventTypes []string) string {
    name := strings.TrimSpace(scenarioName)
    if name == "" {
        return ""
    }
    // L1 精确相等
    for _, t := range eventTypes {
        if t = strings.TrimSpace(t); t != "" && name == t {
            return t
        }
    }
    // L2 最长整词包含（按字面长度降序，避免短词抢走长词）
    best := ""
    for _, t := range eventTypes {
        t = strings.TrimSpace(t)
        if t == "" {
            continue
        }
        if strings.Contains(name, t) && len([]rune(t)) > len([]rune(best)) {
            best = t
        }
    }
    if best != "" {
        return best
    }
    // L3 保留原有"前两字包含"兜底，供 S01–S08 的历史命名使用
    for _, t := range eventTypes {
        t = strings.TrimSpace(t)
        if r := []rune(t); len(r) >= 2 && strings.Contains(name, string(r[:2])) {
            return t
        }
    }
    return name
}
```

**为什么必须保留 L3 而不能直接删**：S02 场景名是"内网横向渗透/账号泄露"，并不整词包含 `内网渗透`，现在正是靠"内网"两字兜底才归到 `内网渗透`；S07"外网边界防火墙被突破"同理靠"边界"归到 `边界突破`。删掉 L3 会直接改变 S01–S08 的台账展示，违反"不许碰 S01–S08"。

### 4.2 分类：13 部全部归"数据安全演练"

- 理由一：脚本集本身是《数据安全应急演练脚本集》，13 节是同一个专项，拆到"网络安全演练"会破坏"13 节 = 13 部"的对账关系。
- 理由二：S01–S08 已有 8 部网络安全演练，其中 S01 勒索病毒、S06 数据泄露与 §14、§5 主题接近；若把 §14 标成网络安全，会和 S01 撞题材，且用户会说"又混进网络安全里了"。
- 边界说明：**§7 数据拦截、§14 数据加密勒索** 技术上具备网络攻击特征（链路监听、勒索软件），但事件客体是"数据"，且要与 S01 区分，因此仍归数据安全。若评审坚持二分，只有 §7 可改挂网络安全，**但会打破 13 节完整性，不建议**。

### 4.3 节点数：20–24 的正确节点，不是 18

- 现有 0108 每部 18 个正确节点（17 计分 + 1 end），来自"合并动作"；B 要逐条对账，18 装不下（审计 6.2 已核：13 节有效动作均 ≥ 20）。
- 本方案定 **20–22 个正确节点**（19–21 计分 + 1 end），落在用户给的 20–24 区间下限附近，理由是：
  1. 客流/节点越少，`quality_rules` 和评估校准越可控；
  2. 13 部 × 22 ≈ 286 行，加干扰项约 330 行，已是 0108 的 2.5 倍，仍可拆成 3 个迁移；
  3. 缺口节点（§4 假冒识别、§7 换密钥、§8 模型回滚、§10 DDL 管控、§11 会话封禁、§12 冻结使用、§13 接口封禁、§15 分级补救）已全部计入。
- 干扰项统一 **4 个/部**（3/5/8 分），合计 52 个；若某部想要 5 个，从相邻部调剂，总量控制在 50–55。
