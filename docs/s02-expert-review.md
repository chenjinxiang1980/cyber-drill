## 0. 机制与口径确认（与 S01 对齐）

1. 剧本定义表是 `script_nodes`；`drill_steps` 只是运行记录，改剧本不会改历史记录。
2. 主流/混淆共用一张表，靠 `flow_type=correct/distractor` 区分；混淆必须通过 `anchor_id` + `release_timing(before/after)` 放行。
3. 评分起点 100，`maxScore` = 正确节点分值合计（`type=end` 不计）；超时扣节点分 20%，接收人错误扣 30%，处置质量占节点分 20%，单节点扣减上限 80%。
4. 混淆档位服务端只允许 `{3,5,8}`，默认中档 5；混淆扣分即该节点分值。
5. 表单必填由服务端强校验，缺字段返回 400；表单内容不直接计入总分，但决定 20% 的处置质量分。
6. 实战版只下发"本角色可办 + 已放行"节点，且外部角色 403；基础版任务按 `seq` 串行生成，展示 `guide`。
7. 基础版/实战版任务只对"演练中"放行；脚本查看门控属于代码层，与剧本数据无关。

**S02 现实状况**：`descr` 全部为空、`short_title` 全部为 NULL、混淆分值全部为 10（不在 `{3,5,8}` 内）、无 `type=end`、只有 1 个节点绑表单且绑错表单。这不是"内容偏弱"，而是**实战版只能看标题猜对错、质量分几乎无法计算**。

## 2. 最致命问题（按危害排序）

### 2.1 合规倒挂：报案被"外部意见"卡住，而"直接报案"被判错（P0，必须改）

- 正确节点 S02-12 标题是"根据市卫健局+网信办意见确定是否报市网安大队立案取证"，`deps=["S02-8","S02-9"]`。
- 混淆 `DSS02-itlead-12-2` 是"直接报案，让网安大队介入调查"，被当成错误答案。
- 结果：演练训练出来的行为是"**先等卫健、网信回复，再决定要不要报案**"。这与 S01 已经纠正的"先行报案、不等待外部研判"完全相反，属于**练错合规动作**，比内容空更严重。

### 2.2 把正确动作设为混淆（6 条，P0）

| 混淆节点 | 现标题 | 为什么是正确动作 |
|---|---|---|
| DSS02-duty-1-1 | 先查登录时间是否和该账号值班表对得上 | 排除本人值班/异地登录是核实第一步 |
| DSS02-netsec-2-2 | 直接从 WAF 和 IPS 日志反查登录 IP 归属 | 这是"登录来源核实"的标准手段 |
| DSS02-itlead-3-1 | 先查有没有多个账号被类似方式盗用 | 横向排查意识正确，应作为研判要点 |
| DSS02-netsec-7-1 | 先看该账号登录过哪些主机，主机上有没有异常 | 横向渗透排查的标准入口 |
| DSS02-itlead-9-1 | 先报初步情况，后续处置进展再动态更新 | 这正是"初报 + 续报"的规范上报方式 |
| DSS02-itlead-12-2 | 直接报案，让网安大队介入调查 | 重大/较大事件先行报案是正确行为 |

### 2.3 证据链倒挂、缺恢复环节（P0）

- S02-11（取证）`deps=["S02-6","S02-7"]`，与 S02-10（隔离封堵）同级；没有"先取证再恢复/再清除"的约束。
- 主链没有"业务/账号恢复验证"节点，S02-13 直接宣布结束；结束后无法回答"账号权限是否回收、业务是否验证"。
- 取证节点没有下游，做与不做对结束没有影响，参演人可以整段跳过。

### 2.4 内容层与表单层同时失守（P0）

- 13 个主流节点 `descr` 全空、`short_title` 全 NULL；26 条混淆 `descr` 全空。
- 只有 S02-4 绑 F8，且 F8 是"事件反馈单"（7 个 textarea），与"报告并建议启动"动作不匹配；启动、隔离、取证、上报、报案、结束全部无表单。
- 质量分占 20%，但 12/13 节点没有表单必填可校验，实际质量分只能靠 `measure` 文字长度，等于没有。
