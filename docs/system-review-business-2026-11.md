# 网络安全应急演练系统业务与剧本专业性评审（2026-11）

**评审对象**：网络安全应急演练系统 v0.6.0（现网 `192.168.97.131:8090`，本机经 `127.0.0.1:8090` 只读访问）
**评审范围**：演练流程闭环、S01–S08 剧本（348 个节点）、F001–F018 表单、评分与复盘、干扰项/混淆节点
**评审方式**：只读查看仓库代码、迁移与文档；只读访问现网公开大屏接口；引用 P2026-001 现场记录。未写库、未改代码、未重启容器、未推仓库。
**评审日期**：2026-11-07

## 0. 结论摘要

系统已经具备“告警—核实—研判—启动—处置—恢复—取证—上报—结束”的骨架，S01–S08 共 348 个节点（正确 128、干扰 220），表单、角色、证据、评分规则均已结构化，具备可演练的基础。但从业务专业性和演练可信度看，当前存在三类结构性问题：

1. **闭环在“结束”和“复盘”两处断裂**：结束被做成 35–48 项取证硬门禁，真实演练中几乎不可完成；复盘节点又被 `type='end'` 过滤，不进入任务、不进入评分。
2. **“取证”存在两套互不相通的口径**：评分按文本里出现证据名称给分，结束按 `evidence` 表归档数量卡门禁。结果是 P2026-001 出现“0/35 证据、95.8 分、优秀、却无法用 `/api/drill/finish` 结束”的悖论。
3. **结束条件与真实应急权责边界不一致**：S01–S08 的结束节点普遍依赖“公安受理回执”，部分剧本又缺少“双报”依赖；S05、S08 的“条件报案”被写成“强制报案+强制回执”，会误导参演人员。

**分级统计**：P0 11 条、P1 16 条、P2 9 条；需用户裁决 7 项。

**最优先处理的 5 件事**：
- 把“结束”统一为一个服务：核心证据分级 + 有缺项结束 + 结束审批 + 评分封存 + 时间线落痕（P0-01/02/03）。
- 让评分读取 `evidence` 表，而不是只在文本里找证据名；给证据完整率设等级上限（P0-04）。
- 把复盘节点从 `end` 改为可执行、可评分的任务（P0-05）。
- 调整 S01–S08 结束依赖：去掉公安回执、补上双报（P0-06/07）。
- 修掉评分绕过和实战版超时计时错误（P0-09/10）。

## 3. P0 必须修改（影响演练可信度或会导致错误指引）

### P0-01 结束取证硬门禁按全项目 35–48 项、且包含未执行节点，真实演练无法正常收口

**问题现象**
- 结束按钮只有在“取证材料全部归档”时才可用；只要有一项未归档，按钮禁用并提示“不可结束演练”。
- 取证统计按**全剧本所有正确节点的全部 evidence_req** 计算，不区分节点是否执行、是否属于核心证据。S01 为 35 项，S07 为 48 项，S08 为 47 项。
- P2026-001 处置动作在 11:46 已完成，但因 0/35 证据，直到 13:51 只能改状态收口。

**证据**
- `server/internal/handler/drill_v1.go:181-227`：`loadEvidenceSummary` 查询 `script_nodes WHERE scenario_id=? AND type!='end'`，对每个非干扰节点的每一条 `evidence_req` 累加 `Total`，**不 join 任务/步骤状态**，因此未执行节点的证据也计入 `Pending`。
- `server/internal/handler/drill_v1.go:681-692`：`if ev.Pending > 0 { 400 "取证未完成" }`。
- `public/workbench.html:1694-1697`：`EV.pending > 0` 时 `btnFinish.disabled = true`，标题“尚有 N 项取证材料未归档”。
- `public/workbench.html:1864-1866`：再次 toast“取证材料尚未完成归档……不可结束演练”。
- 现场：S01 35 项、`evidence` 表 0 项、`/api/drill/finish` 400。

**专业依据**
- 《医疗卫生机构网络安全管理办法》（国卫规划发〔2022〕29 号）要求医疗卫生机构建立网络安全事件应急处置和报告制度，但未要求“所有支撑材料 100% 归档后才能宣布响应结束”。
- 《国家网络安全事件应急预案》4.4 的应急结束条件是“应急处置工作结束，或者相关威胁和危害得到控制、消除”，不是“取证材料全部归档”。
- 真实演练中证据缺口是常态，正确做法是**分级取证 + 缺项说明 + 审批**，而不是一刀切阻断。

**具体修改建议**
1. 在 `evidence_req` 条目上增加 `level` 字段：`core`（结束前必须核对）/`support`（计入评分，不阻断结束）。建议每个剧本 core 控制在 10–12 项：
   - 告警/核实：1 项（可设为 support，不阻断）。
   - 研判/启动：1 项（定级意见或启动令）。
   - 关键处置：2–3 项（隔离清单、备份校验、取证清单）。
   - 双报/报案：1–2 项（上报回执/受理编号）。
   - 恢复/结束：2 项（恢复验证、结束记录）。
2. `loadEvidenceSummary` 改为只统计**已完成节点**的 core 证据；未执行节点不计入 `Pending`，其证据缺口通过评分扣分体现。
3. 结束接口增加“有缺项结束”分支：
   - `POST /api/drill/finish` body 增加 `exception: { reason, itemKeys[], remediationDeadline, approver, approvedAt }`。
   - 有缺项且提供了合法 exception：允许结束，状态写 `已结束（有缺项）`，返回 `missingEvidence[]`。
   - 无 exception 且 core 缺失：返回 409，body 带 `missingItems[]`，前端展示清单，而不是只给一句“取证未完成”。
4. 前端结束弹窗改为三段式：
   - “必做节点完成 X/Y；未完成项将按节点分值扣分”。
   - “核心证据 X/Y；缺失 N 项（列出节点、证据名、责任人）”。
   - 两个按钮：“补齐后结束”“有缺项结束（填写原因/责任人/补录时限）”。
5. `timeline` 写入“演练结束（有缺项）”并附 `missingEvidence` 摘要；结束报告首页展示“核心证据完整率、缺项数、补录时限”。
6. 等级上限：核心证据完整率 <100% 不得评“优秀”；<80% 不得评“良好”；有缺项结束必须在报告中标注。

**验收标准**
- 用 S01 造一个“完成 17 个节点、核心证据 8/12”的项目，可走“有缺项结束”，生成缺项清单和 `已结束（有缺项）` 时间线。
- 未执行节点的证据不再出现在 `Pending` 中。
- 0/35 证据不能再以“优秀”收口。

### P0-02 三条结束路径并存，基础版只能改状态，时间线与评分丢失

**问题现象**
- 实战版走 `POST /api/drill/finish`：有取证门禁、写 `timeline`、不写 `scores`。
- 管理页“结束演练”走 `PATCH /api/projects/:id/status`：无取证门禁、不写 `timeline`、不写 `scores`。
- 另有 `POST /api/drill/projects/:id/end`：无取证门禁、写 `timeline`、只写一条 `scores` 汇总。
- 基础版工作台没有“完成演练”按钮（按钮仅在 `isPractical` 时渲染），因此基础版**只能**走状态接口；P2026-001 正是如此。

**证据**
- `public/projects.html:99`：`changeStatus(p,'已结束','结束演练《'+p.name+'》')`；`projects.html:176-183` 调用 `API.updateProjectStatus`。
- `public/workbench.html:150-151`：`isPractical && proj.status==='演练中' && ['commander','platformadmin','itlead']` 才显示 `btnFinish`。
- `server/internal/handler/missing_handlers.go:886-925`：状态更新只改 `projects` 并发送通知，不写 `timeline`、不写 `scores`。
- `server/internal/handler/drill_v1.go:697-719`：finish 写 `timeline`，但 694-752 没有写 `scores`。
- `server/internal/handler/drill_runtime.go:216-250`：另一条结束路径写 `timeline` 和 `scores` 的 `MODE` 行。
- 现场：P2026-001 `timeline` 仅 1 条创建记录。

**专业依据**
- 演练结束是审计事件，必须留下“谁、何时、依据什么、以什么状态结束”的统一记录；多入口不同副作用会导致台账不可信。
- 基础版和实战版可以有不同的取证要求，但不能有不同的“结束记账”规则。

**具体修改建议**
1. 新增统一服务 `FinishDrill(projectId, mode, exception)`，所有结束入口只调用它：
   - 校验项目状态；
   - 计算/校验 core 证据；
   - 写 `timeline`（`action='演练结束'`，detail 含状态、评分快照 ID、缺项数）；
   - 写评分快照（见 P0-03）；
   - 发送结束通知。
2. `POST /api/drill/finish` 与 `POST /api/drill/projects/:id/end` 都改为该服务的薄封装；`EndProject` 不再单独写 `scores`。
3. `PATCH /api/projects/:id/status` 禁止直接把状态改为 `已结束`/`已归档`：返回 409 `USE_FINISH_API`，或要求 `reason` 并内部调用 `FinishDrill(force=true)`，同样写时间线和快照。
4. 基础版工作台增加“完成演练”按钮（角色限 commander/platformadmin/itlead），与实战版共用同一结束弹窗；基础版的证据要求可降为 core 子集。
5. `projects.html` 的“结束演练”改为打开结束弹窗，而不是直接改状态；“归档”只能从“已结束”进入，且不得绕过快照。

**验收标准**
- 三条路径结束同一项目，`timeline`、`scores`/快照、通知三者结果一致。
- 基础版不再出现“只有创建记录、没有结束记录”的项目。
- 任何“已结束”项目必有 `score_snapshot_id`。

### P0-03 评分未封存，`scores` 表无快照与规则版本，报告不可追溯

**问题现象**
- `Score()` 是按需计算的纯函数；结束时不落评分快照。
- `scores` 表只有 `item_id/project_id/score/max/note/auto/updated_at`，没有规则版本、扣分明细、证据完整率、封存时间。
- 复盘页和报告每次打开都重新计算；剧本/规则一旦修改，历史演练的分数会变化，无法复现。

**证据**
- `server/internal/handler/drill_score.go:416`：`Score()` 为纯计算，不写库。
- `server/internal/handler/drill_v1.go:694-752`：finish 只更新状态、写 timeline、发通知，无 `scores` 写入。
- `server/internal/handler/drill_runtime.go:242-250`：只写一条 `scores` 汇总（`MODE`），无明细。
- `server/internal/handler/drill_runtime.go:593-595`：`RecalcProjectScore` 会**覆盖**同一条 `MODE` 行，没有版本号；任何人点“重新自动考评”，历史分数即被改写。
- `migrations/0001_init.up.sql:349-359`：`scores` 表字段不足以承载快照。
- `public/evaluation.html` 直接调用评分接口，未读取封存快照。

**专业依据**
- 演练报告是对上汇报、复盘整改的依据，必须可追溯“当时用的哪版剧本、哪版评分规则、扣了哪些分”。
- 规则变更后重算历史分数，等于篡改历史结论。

**具体修改建议**
1. 新增 `score_snapshots` 表（或扩展 `scores` 并增加 `snapshot_id`），建议字段：
   - `id, project_id, mode, score, grade, max_score, hit, total, completeness, time_rate, evidence_complete_rate, evidence_exception_count`
   - `deductions_json`（逐节点：节点号、分值、超时/接收人/关键词/文本/证据各扣多少、原因）
   - `nodes_json`（逐节点完成/跳过/误选/超时）
   - `exceptions_json`（缺项清单、原因、审批人、补录时限）
   - `rule_version`（对 scenario 节点 JSON + quality_rules 做 SHA-256）
   - `scenario_version, sealed_at, sealed_by`
2. 在 `FinishDrill` 中只计算一次 `Score()`，写入快照并置为“已封存”；报告/复盘页只读快照。
3. 需要重算时，创建新版本（`version+1`）并记录“重算人/原因”，不得覆盖旧快照。
4. 结束报告页脚固定展示：“评分封存时间 / 规则版本 / 取证完整率 / 缺项数”。

**验收标准**
- P2026-001 在规则修改后重新打开报告，分数、扣分明细、等级与 13:51 封存时一致。
- 任意“已结束”项目都有唯一 `sealed_at` 和 `rule_version`。
- 重算产生新版本，旧版本仍可查。

### P0-04 取证评分按文本命中、归档按 `evidence` 表，0/35 仍得 95.8 优秀

**问题现象**
- 评分中的“证据”只看提交文本里是否出现证据名称；只要写了“已提交告警截图/日志”，就视为证据齐全。
- 结束门禁看 `evidence` 表实际归档；0 项就 400。
- 两者互不相通，导致“评分满分、结束卡死”的悖论；P2026-001 0/35 证据仍得 95.8 优秀。

**证据**
- `server/internal/handler/score_config.go:961-975`：`missingEvidence := EvidenceText == ""`；非空且 `evidenceRequirementHit(EvidenceReq, q.Text)` 即视为命中。
- `server/internal/handler/score_config.go:715-727`：`evidenceRequirementHit` 只检查证据名称中的任一 token 是否出现在 `q.Text`（`measure/result/found/evidence` 合并文本）。
- `server/internal/handler/drill_score.go:895-915`：把 `EvidenceText` 传入扣分函数。

### P0-09 评分可被关键词/证据文本堆砌绕过

**问题现象**
- `bonusKeywords` 每命中 1 个可抵扣 1 个必含关键词缺失，且可**全额抵消**；只要写满加分词，必含动作一个不写也不扣关键词分。
- 证据分只要文本里出现任一证据名称即通过；文本质量只看长度和“对象/动作/结论”等宽泛词。
- 单节点扣分上限 80%，即使全部维度都错，仍保留 20% 分值。
- 结果是“堆关键词 + 写证据名”即可拿高分，和真实处置能力脱节。

**证据**
- `server/internal/handler/score_config.go:61-62`：注释明确“每命中 1 个可抵扣 1 项必含缺失的比例”。
- `server/internal/handler/score_config.go:896-915`：`effective := len(missing) - bonusHits`，可降到 0。
- `public/scenarios.html:1244`：后台编辑界面直接写“加分关键词（可抵扣必含缺项）……每命中 1 个，可抵扣 1 个必含缺失项”。
- S01-5 的 `quality_rules`：必含 3 组、加分 3 组；只写加分词即可免关键词扣分。
- `server/internal/handler/score_config.go:961-975`：证据文本任一 token 命中即通过。
- `server/internal/handler/score_config.go:23-35`：`timeout 0.2 / receiver 0.3 / keyword 0.3 / text 0.2 / evidence 0.2`，`NodeMaxPenaltyRatio=0.80`；`capNodeParts` 在 `467` 行施加封顶。

**演示**
以 S01-5 为例，写一段“重大事件，受影响科室范围扩散趋势，数据量较大，按Ⅱ级处理，已研判，定级意见已形成，影响评估记录已提交”，即可同时命中加分词和证据名，即使没有写“定级依据/患者安全”等必含动作，也可能拿到关键词和证据满分。这不是专业处置，是文本应试。

**专业依据**
- 演练评分应衡量“是否采取了正确动作、是否留下证据、是否在时限内”，而不是“是否说了关键词”。
- 关键词只能作为辅助检索，不能替代判据槽、证据和时序。

**具体修改建议**
1. 加分词抵扣上限：最多抵扣 1 组必含缺失，或最多抵扣 30% 关键词扣分；不得全额抵消。
2. 必含关键词改为“动作+对象”组合（如“隔离+感染主机”“核对+恢复点”“固定+样本/日志”），避免“重大/恢复/上报”这类单词。
3. 证据分改为读 `evidence` 表；文本证据名只作为 50% 降级分，且必须同时有归档记录。
4. 增加“实质性动作”门槛：若某节点必含动作命中 0 且无归档证据，该节点得分直接为 0，不受 80% 封顶保护。
5. 文本质量增加“反堆砌”规则：关键词密度、无标点长串、动作词与对象词不匹配时扣分；对“只列关键词”的文本直接判低分。
6. 增加 3 组反作弊测试用例（S01-5 关键词堆砌、S02-8 只写证据名、S06-9 只写“已排查”），纳入回归。

**验收标准**
- 只写加分词/证据名的 S01-5 文本得分低于 60，且证据分为 0。
- 正确写动作但用词不同义的文本，仍能通过判据槽获得合理分。
- 80% 封顶不再保护“零实质动作”的提交。

**问题现象**
- 实战版提交时用 `isLateV1(p,node)` 判断超时；该函数以**项目开始时间**为起点，而不是“前置节点完成时间”。
- `Score()` 又直接使用步骤里存的 `s.Ontime`，不重新按依赖计算；精确的 `isLate()` 函数存在但未被使用。
- 结果：一场 60 分钟的演练，凡 `timeout` 为 15 分钟的节点，在开始 15 分钟后提交都被判超时，即使它的前置节点在第 50 分钟才完成、参演人员立即处置。
- 暂停时间也没有从超时计算中扣除。

**证据**
- `server/internal/handler/drill_v1.go:1123-1143`：`isLateV1` 用 `p.StartedAt` 作为 `startMs`，`now.Sub(startMs) > node.Timeout`。
- `server/internal/handler/drill_v1.go:505`：`ontime := !isLateV1(p, node)` 写入步骤。
- `server/internal/handler/drill_score.go:533-536`：`"late": s.Ontime == 0`，Score 信任存储值。
- `isLate()` 精确函数存在但未被 Score 调用。
- `nodeStartMsBasic` 与 `isLate` 均未扣 `paused_sec`。

**专业依据**
- 应急处置时限应按“上一环节完成/指令下达”起算，不能按演练开始一刀切；否则后段节点必然超时，评分失真。
- 暂停期间不应计入处置时限，这是演练计时器的基本公平性。

**具体修改建议**
1. `Score()` 改为按依赖实时计算：`late := isLate(p, node, stepCreatedAt)`；删除对 `s.Ontime` 的依赖，或把 `s.Ontime` 作为展示字段、不作为评分依据。
2. `isLate()` 的起点取所有 `deps` 完成时间的最大值；无 deps 的节点取项目开始时间；再减去 `paused_sec`（或按暂停区间累计扣除）。
3. `isLateV1` 如仍用于即时提示，改为同样的依赖起算逻辑，避免“提交时提示超时、评分时又不一致”。
4. 增加单元测试：
   - 60 分钟演练，节点前置在第 50 分钟完成、timeout 15，立即提交不应超时；
   - 暂停 30 分钟，恢复后节点不应因暂停被扣超时；
   - 并行节点各自从共同前置完成时起算。

**验收标准**
- 实战版后段节点不再因项目总时长被批量判超时。
- 暂停前后同一节点的剩余时限连续。
- UI 提示与评分结果一致。

### P0-11 复盘页/评分说明与后端口径不一致，报告会输出错误扣分解释

**问题现象**
- 复盘页硬编码“偏离每项扣 20 分、超时每项扣 10 分、未处置每项扣 15 分、额外操作每项扣 5 分”，后端实际是按节点分值扣分 + 超时 20% + 接收人 30% + 关键词 30% + 文本 20% + 证据 20%。
- 基础版说明写“仅统计处置时长达成率”，但后端还会因未完成节点扣满分值，实际是“完成度 + 时限”。
- 复盘建议因此会给出错误的扣分解释，对外报告不可信。

**证据**
- `public/evaluation.html:166-168`：硬编码“未处置基线必经环节（扣15分）/偏离（扣20分）/超时（扣10分）”。
- `public/evaluation.html:213-216`：自动建议文本再次使用“每项扣20/10/15/5分”。
- `public/evaluation.html:187`：基础版说明“仅统计处置时长达成率”。
- `server/internal/handler/score_config.go:23-35`：实际比例 0.2/0.3/0.3/0.2/0.2，节点分值为 3/5/6/7/8 不等。
- 现场：S01 总分 95.8，3 个节点超时；按页面“每项扣10分”应扣 30 分，实际只扣约 4.2 分。

**专业依据**
- 复盘报告是整改依据，扣分口径必须与评分引擎一致；说明书与引擎不一致会直接误导整改方向。
- 对外汇报的分数解释应可逐项复算。

**具体修改建议**
1. 复盘页不再硬编码扣分数值，改为读取 Score 返回的 `deductions`/节点明细，显示“节点权重 X 分，扣 Y 分，原因：超时/接收人/关键词/文本/证据”。
2. 基础版说明改为“按节点完成情况与时限达成率计分；未完成节点按分值扣分”。
3. 增加一段“评分口径”折叠说明，列出当前模式的真实公式、各维度比例和封顶规则。
4. 结束报告导出时，附“评分口径版本/规则版本”，与快照一致。

**验收标准**
- 任取一个超时节点，复盘页显示的扣分与 Score 明细一致。
- 基础版不再出现“仅统计时长”的表述。
- 报告中的扣分解释可逐项复算到总分。

## 4. P1 应当修改

### P1-01 报告节点时限 15 分钟与制度 1/2 小时冲突

**现象**：S02-8 标题“2 小时内报市卫生健康局”，S03-6/S04-7/S07-7/S08-7 描述“2 小时内”，S01-8/S05-6/S05-7/S06-6/S06-7 描述“1 小时内”；但这些节点的 `timeout` 全部是 15 分钟。参演人员 30 分钟内完成上报，符合制度却在系统中被判超时。

**证据**：现场 S01-8 `timeout=15`，标题“同时报市卫生健康局和市网信办”；S02-8/S03-6 等同样 `timeout=15`；描述中明确写 1/2 小时。

**依据**：《网络安全事件报告管理办法》《国家网络安全事件应急预案》规定的是**制度时限**；演练可以压缩，但必须明确“演练时限”与“制度时限”双轨。

**建议**：报告节点 `timeout` 改为制度时限（60/120 分钟），或在节点文案/计时器上明确“演练压缩时限 15 分钟，制度时限 1/2 小时”；评分超时按演练时限，但报告解释必须区分两者。更推荐前者，避免“合规却超时”。

### P1-02 接收人精确匹配、自己接收、医务处抄送导致 30% 权重失真

**现象**
- 接收人评分要求“选中集合与配置集合完全一致”，多选一个合法接收人也会扣 30%。
- 基线快照中有 23 个正确节点 `target == receiver`（无 `receiver` 为空的节点）；这些节点的接收人评分没有区分度。
- S06-6/S06-7 的接收人含“医务处”，但标题只说“报市卫生健康局/市网信办”；只报外单位会被扣 30%。

**证据**
- `server/internal/handler/drill_v1.go` 的 `parseReceivers` 排序后做集合相等比较；`drill_score.go` 的 `receiverOk` 直接取该结果。
- S02-7、S03-8、S05-9、S06-11、S01-17 等 `target=receiver`；S06-6/7 `receiver` 含医务处。

**依据**：接收人评分应考“是否报给正确主体”，不应惩罚“多报一个合法协同岗位”；自己给自己的节点不应占 30% 权重。

**建议**：
- 报告类节点接收人校验改为“必须包含配置主体；额外合法协同岗位不扣分”，并维护允许集合。
- `target==receiver` 的节点关闭接收人维度，把 30% 权重并入文本/证据/时限。
- S06-6/7 的医务处改为“抄送（可选）”，与“接收人（必选）”分离。

### P1-11 干扰项分值未按风险严重度校准

## 5. P2 建议优化

### P2-01 告警节点 0 分，监测发现能力未被评价
`alert` 节点 0 分，只有标题/描述，没有评分或证据要求；监测发现、告警确认、初判没有进入评分。建议给告警确认 2–3 分（或把首个核实节点的证据分与告警确认绑定），否则“风险监测”阶段只是形式。

## 6. 评分与复盘口径评审（汇总）

### 6.1 当前评分公式

| 维度 | 比例 | 说明 |
|---|---:|---|
| 超时 | 20% | 节点分值的 20% |
| 接收人错误 | 30% | 选中集合与配置集合完全一致 |
| 关键词缺失 | 30% | 必含关键词缺失，加分词可全额抵扣 |
| 文本质量 | 20% | 长度、要素、填充词 |
| 证据缺失 | 20% | 文本中出现证据名即通过 |
| 单节点封顶 | 80% | 五项合计最多扣 80% |

**问题**：加分词全额抵扣、证据文本化、接收人精确匹配、80% 封顶，四个机制叠加，使“文本应试”可以拿到高分；同时证据归档又不参与评分，导致“高分但无法结束”。

### 6.2 建议的评分口径

1. **节点权重**：保留 3/5/6/7/8 的节点分值，总分 100（或 106 含复盘）。
2. **维度**：
   - 处置正确性/动作完整性 40%（必含动作组合，不是单词）；
   - 证据 20%（读 `evidence` 表，core/support 加权）；
   - 时限 20%（按依赖起算，扣暂停）；
   - 接收人/协同 10%（必须包含，额外合法不扣）；
   - 文本质量 10%（反堆砌）。
3. **封顶**：单节点最多扣 100%（零实质动作可 0 分）；不再保留 20% 保底。
4. **等级**：证据完整率 <100% 不得优秀，<80% 不得良好；核心证据缺失走“有缺项结束”。
5. **复盘**：单独计分或作为必做不计分任务，必须有 F8 + 复盘问题清单 + 指挥部签字。

### 6.3 复盘问题设计建议

当前 F8 是“报告模板”，不是“复盘问题”。建议增加 8 组问题（发现、研判、启动、处置、上报、恢复、取证协同、整改），每组 3–5 个问题，并自动带入：
- 节点实际用时 vs 时限；
- 评分扣分明细；
- 误选干扰项；
- 证据缺项；
- 外部单位协同记录。
复盘会议纪要应能直接从系统导出，整改项要有责任人、时限、验收标准。

### 6.4 结束收尾与评分封存的业务结论（回答 P2026-001）

**结论一：正确机制不是“二选一”，而是“分级取证门槛 + 结束前核对 + 有缺项结束说明”三件套。**

理由：35–48 项全量取证在真实演练中几乎不可完成，若坚持“全归档才可结束”，只会逼出 P2026-001 这种“绕开结束接口改状态”的收口方式；但若完全不设门槛，又会失去演练的取证训练目的。三件套分别解决“门槛太高”“核对不透明”“缺项无留痕”三个问题。

| 机制 | 规则 | 是否阻断结束 |
|---|---|---|
| 分级取证 | 每个剧本设 10–12 项 `core`（告警确认、定级意见、启动令、隔离清单、备份校验、双报回执、恢复验证、结束记录等），其余为 `support` | 仅 core 缺失时阻断 |
| 结束前核对 | 结束弹窗一次性列出：必做节点完成 X/Y、core 证据 X/Y、缺失项（节点号/证据名/责任人/建议补录时限） | 不阻断，但不可跳过 |
| 有缺项结束 | core 缺失时允许结束，但必须填写 `exception`：缺项原因、缺项 key、补录责任人、补录时限、批准人 | 有合法 exception 才放行 |
| support 缺失 | 不阻断结束，只在评分中扣证据分，并在报告“证据完整率”中体现 | 否 |
| 全量缺失（0 证据） | 不得直接结束；必须走 exception 并降级评级，报告首页显著标注 | 是（除非 exception） |

**状态与留痕规则**
- 项目状态：`演练中 → 结束核对 → 已结束（完整）` 或 `已结束（有缺项） → 已归档`；`已归档` 只能从 `已结束` 进入，且必须已有评分快照。
- `已结束（有缺项）` 必须写 `timeline`：结束人、结束时间、core 完整率、缺项数、exception 批准人、补录时限。
- 补录只能“追加补录记录”，不得回写已封存的评分快照；补录完成后在报告附页记录“补录时间/补录人/新增证据”，原分数与等级不变。
- 结束记录单 F18 的“结束依据”必须逐条对应 core 证据 key；缺项在 F18 中写明“未完成项 + 责任人 + 时限”，不能只写“已基本完成”。

**界面口径（可直接用于文案）**
- 结束按钮禁用时不再只写“取证未完成”，改为：“核心证据 8/12 未齐（缺 4 项），可补齐后结束，或填写缺项说明申请结束。”
- 缺项清单列头：`节点 | 证据名称 | 责任人 | 建议补录时限 | 是否 core`。
- “有缺项结束”按钮文案：“有缺项结束（需填写原因/责任人/补录时限/批准人）”。
- 结束后报告封面：“核心证据完整率 67%（8/12）；有缺项结束；补录时限 2026-11-10 18:00；批准人：XXX”。

**结论二：评分必须在结束时刻封存快照，并带规则版本；报告只读快照，不读实时 `Score()`。**

- 封存时点：`FinishDrill` 内只计算一次 `Score()`，写入 `score_snapshots`，状态置“已封存”；结束通知、结束报告、复盘页统一引用 `snapshot_id`。
- 快照必须含：`score/grade/max_score/hit/total/completeness/time_rate/evidence_complete_rate`、逐节点扣分明细、缺项清单、`rule_version`（剧本节点 JSON + `quality_rules` + 评分比例的 SHA-256）、`scenario_version`、`sealed_at/sealed_by`。
- 重算规则：任何“重新考评”生成 `version+1` 的新快照，旧快照保留；报告默认展示封存版本，可切换查看历史版本及重算原因。
- 评级联动：`core` 完整率 <100% 不得“优秀”，<80% 不得“良好”；有缺项结束必须在等级旁加“（有缺项）”标识，不能只显示“优秀”。
