# 脚本集转演练剧本转化方案

- 上游评审：[数据安全应急演练脚本集评审意见](data-security-scriptset-compliance-review.md)
- 目标系统：网络安全应急演练系统（Go + Gin + MySQL 8，纯静态前端）
- 编制日期：2026-11-09
- 本轮边界：只出方案，不部署、不重启容器、不改现网数据；本机只做编辑与静态检查（`go vet`、`GOOS=linux` 交叉编译、`node --check`），不编译 Windows exe

## 一、目标、原则与硬约束

### 1.1 目标

把脚本集的 13 个事件脚本重构为可导入本系统的数据安全演练剧本：每个剧本具备可判定动作、可归档证据、可评分节点、可设置干扰项，并且法定报告/报案/告知链完整。

### 1.2 五条原则

1. **先合规、后场景**：没有监管上报、刑事报案、个人信息告知节点的剧本，不进入排期。
2. **一事件一剧本**：不把 13 个脚本原样复制成 13 个剧本，按事件客体合并同类。
3. **复用现有口径**：分类、节点、质量规则、证据、评分、回执、角色全部沿用系统现有机制。
4. **对现有剧本零影响**：S01–S08 的内容、节点、分值、依赖、流程、表单、已封存快照一律不改。
5. **可判定**：每个节点必须写清“谁、在什么时限内、对谁、做什么、留什么证据、得多少分、干扰是什么”。

### 1.3 硬约束

- 不修改 `S01`–`S08` 的 `scenarios`、`script_nodes`、`quality_rules`、分值与依赖；
- 不修改已封存快照；
- 新剧本使用新 ID，不覆盖、不重用旧 ID；
- 分类修正只动 `scenarios.category` 元数据，不动节点与分值；
- 不新增第二套评分算法，不改变现有回执判定逻辑。

## 六、其它剧本的差异化节点

### 6.1 S09 第三方/供应链数据泄露

- 触发：供应商运维账号、接口合作方、云服务商、快递/打印外包等；
- 必备节点：合同与委托处理核查（F21）、供应商通知与回执、联合处置、监管双报、个人告知、合同整改/暂停合作；
- 与 S06 的区别：S06 是院内泄露+舆情；S09 是“数据处理者—接收方”链路，必须体现网数条例第12条的合同、监督、记录≥3年；
- 干扰项：只换供应商密码不报告、只追责不告知个人、未核实合同范围就认定责任。

### 6.2 S11 数据篡改/伪造

- 触发：病历、检验结果、检查报告、费用、电子签名、AI 辅助诊断结果被篡改或伪造；
- 必备节点：完整性校验、备份比对、业务影响评估（患者安全优先）、电子签名/时间戳核验、恢复、对外更正/告知、监管报告；
- 与 S10 的区别：S11 的核心是数据完整性，不是数据被拿走；
- 干扰项：只恢复系统不核验业务数据、只改数据不追溯来源、未评估患者安全即对外发布。

### 6.3 S12 数据滥用/违规共享

- 触发：科研/教学/第三方共享超出授权目的、范围、期限；员工私自查询；
- 必备节点：用途与授权核查、停止使用、删除/召回、合同/制度整改、第三方审计、监管报告、个人告知（权益受损时）；
- 与 S10 的区别：S12 不一定“导出”，但“用了不该用的数据”；
- 干扰项：以“科研需要”为由继续使用、只删本地不追第三方、未评估合同违约。

### 6.4 S13 个人信息违规收集/敏感个人信息

- 触发：互联网医院、App/小程序、第三方 SDK 超范围收集；行踪轨迹、健康生理信息等敏感个人信息；
- 必备节点：最小必要评估、告知同意核查、超采清单、停止收集、删除、隐私政策/授权整改、监管报告、个人告知/公告；
- 与 S12 的区别：S13 发生在“收集端”，S12 发生在“使用端”；
- 干扰项：以“用户体验”为由继续收集、只改隐私政策不删数据、未区分敏感个人信息。

### 6.5 S14 数据破坏/勒索

- 触发：勒索软件加密、误删除、备份失效、备份被加密；
- 必备节点：隔离/查杀、备份可用性验证、RPO/RTO 评估、不支付赎金、报案（敲诈勒索/破坏计算机信息系统）、监管报告、数据恢复、个人告知（如数据被窃取）；
- 分类：主分类网络安全，次分类数据安全；
- 干扰项：支付赎金、直接用受感染备份恢复、只恢复不报案、未评估数据是否被窃取。

## 七、复用口径

### 7.1 分类与编号

- `scenarios.category` 写 `数据安全演练`；S14 写 `网络安全演练`；
- 新剧本 ID 用 `S09`–`S14`，因为新建剧本的 ID 自增依赖 `SUBSTR(id,2)`（[content_write.go](../server/internal/handler/content_write.go#L98)）；
- 节点 ID 用 `S10-1`、`S10-2`；干扰项用 `DS10-3-1`，与现有 `DS{S}-...` 约定一致；
- 不加 `DS01` 前缀，避免与干扰项前缀混淆，也避免 ID 自增解析失败。

### 7.2 节点与质量规则

节点字段沿用：`type`、`flow_type`、`role_id`、`receiver`、`receiver_cc`、`deps`、`release_timing`、`timeout`、`score`、`quality_rules`、`evidence_req`。

`quality_rules` 示例（数据安全节点）：

```json
{
  "requiredKeywords": ["数据类别", "量级", "敏感个人信息", "告知", "回执"],
  "bonusKeywords": ["重要数据", "出境", "删除证明", "保管链"],
  "minMeasureLen": 20,
  "minResultLen": 12,
  "requiredElements": ["对象", "时限"],
  "fillerWords": ["无", "已处理", "按预案"],
  "fillerMaxLen": 8,
  "textQualityRatio": 0.15,
  "keywordPenaltyRatio": 0.25
}
```

`evidence_req` 示例（报告节点）：

```json
[
  {"type": "上报材料", "name": "F2 初报", "note": "含上报对象、时限依据、数据量级"},
  {"type": "回执", "name": "F15 外部意见/回执", "note": "含接收时间、回执编号、是否立案"}
]
```

### 7.3 证据

- 关键节点必须写 `evidence_req`，不能只写“记录/留痕”；
- 证据包至少包含：时间戳、操作人、日志/截图、样本 sha256、回执编号、告知记录、删除/匿名化证明、备份校验记录；
- 复用 `evidence` 表的 `sha256`、`custodian`、`sealed_at`、`chain_of_custody`，不新增证据表。

### 7.4 表单

| 表单 | 用途 | 节点 |
|---|---|---|
| F2 网络安全事件上报表 | 监管双报、初报/续报/终报、回执编号、个人信息字段 | S09/S10/S11/S12/S13/S14 |
| F3 业务影响评估表 | 业务影响、影响数量 | 定级节点 |
| F4 应急启动审批单 | 启动审批 | 启动节点 |
| F5 报案登记表 | 刑事报案 | S10/S11/S14 |
| F8 事件反馈单 | 结束、双报完成时间、证据完整率、干扰项数 | 结束节点 |
| F13 取证清单 | 证据固定 | 取证节点 |
| F15 外部单位意见 | 监管意见、是否立案、承办警官 | 上报/报案节点 |
| F18 复盘报告 | 复盘整改 | 复盘点 |
| **F19 数据安全事件定级与影响评估表**（新增） | 数据类别/级别、量级、字段、敏感个人信息、重要数据、出境、影响 | 定级节点 |
| **F20 个人信息泄露告知记录**（新增） | 告知对象、渠道、模板、发送时间、成功/失败、公告、豁免评估 | 告知节点 |
| **F21 第三方/委托处理事件通知与回执**（新增） | 供应商、合同编号、处理活动、通知时间、回执 | S09/S10-13 |

F19/F20/F21 只新增 `form_templates` 数据，前端动态渲染，不需要改代码。

### 7.5 评分

- 以 100 为扣分基数（[drill_score.go](../server/internal/handler/drill_score.go#L735)），新剧本正确节点分值合计控制在 100 以内；
- 现有 S01–S08 节点分合计约 99–112（0100 后），**不改**；新剧本不复制“超 100”的分值；
- 干扰项分值按现有规则计入，不新增第二套算法；
- 法定时限单独作为 `quality_rules` 的必填要素，不靠节点 `timeout` 表达 1h/4h。

### 7.6 回执与外部意见

- 沿用现有 7 组字典口径与 F2/F15/F5 判定，不改判定逻辑；
- 外部单位使用现有 `healthbureau`、`cac`、`cyberpolice`，`external=1`，由信息科负责人代填；
- 第三方/供应商一期不新增角色：在 S09/S10-13 用 F21 记录供应商名称、联系人、回执，接收人仍为信息科负责人；
- 二期如需要“供应商”独立席位，再加 `vendor` 角色（`external=1`），不改现有角色。

### 7.7 角色映射

| 数据安全职责 | 现有角色 | 说明 |
|---|---|---|
| 总指挥/决策 | 院应急指挥部 | 启动、升级、结束 |
| 数据安全牵头 | 数据安全管理员 | 定级、删除/追回、整改 |
| 技术处置 | 网络安全管理员、系统管理员 | 停止导出、封禁接口、恢复 |
| 业务影响 | 信息科负责人 | 业务影响、对外报告 |
| 患者告知 | 医务处 | 告知对象、临床口径 |
| 对外口径/舆情 | 院办 | 公告、媒体、患者沟通 |
| 合规/报案 | 法务 | 告知审查、报案必要性、合同 |
| 监管/公安 | 市卫健局、市网信办、市网安大队 | `external=1`，信息科负责人代填 |

一期不新增角色；如演练要求“供应商独立应答”，再评估 `vendor`。

### 7.8 干扰项

每个剧本 3–5 个，绑定到具体节点与释放时机：

- 定级类：误判为普通网络事件、漏判敏感个人信息、漏判重要数据；
- 报告类：只报院内、只报一个监管、超过时限、未留回执；
- 报案类：一律不报案、未评估即报案；
- 告知类：以舆情为由不告知、只公告不逐一通知、未评估豁免；
- 证据类：先删除后取证、只留截图不留哈希、证据无保管人；
- 处置类：支付赎金、用受感染备份恢复、只改配置不排查横向。

## 八、需要改代码或加字段

## 十二、结论

一期完全可以在**不改代码、不动 S01–S08**的前提下，用迁移数据落地 6 个数据安全剧本（S09–S14）和 1 个分类修正（S06）。真正需要先解决的不是技术，而是脚本集里的合规链：法定报告、刑事报案、个人信息告知、证据保全。只要这四件事在剧本节点里成立，现有系统的分类、证据、评分、回执与角色机制足以承接；反之，如果继续沿用“只报领导小组、告知只做模拟”的写法，新剧本只会把同样的合规空洞复制到系统里。
