## 0. 机制与口径确认（与 S01 对齐）

1. `script_nodes` 是剧本定义，`drill_steps` 是运行记录；本评审只针对前者。
2. 混淆通过 `anchor_id` + `release_timing(before/after)` 放行；不得引入新门控语义。
3. 评分起点 100，`maxScore` = 正确节点分值合计（`end` 不计）；超时 20%、接收人错误 30%、质量 20%、单节点上限 80%。

5. 表单必填服务端强校验；表单内容不直接计分，但决定 20% 质量分。
6. 实战版只下发"本角色可办 + 已放行"节点；外部角色 403。基础版按 `seq` 串行生成并展示 `guide`。
7. 任务只对"演练中"放行；脚本查看门控属代码层。

**S03 现实状况**：`descr` 全空、`short_title` 全 NULL、混淆全 10 分、无 `end`、只绑 1 张错位表单；**全链没有任何取证节点**。这决定了 S03 目前既练不出"先止损还是先取证"的判断，也练不出"报案要交什么"。

## 2. 最致命问题（按危害排序）

### 2.1 全链没有取证节点，报案与复盘无证据支撑（P0）

13 个主流节点里没有任何"证据保全/日志固定"动作。S03-10"溯源攻击源并封禁 IP"只留下"操作日志"，S03-8"清洗限速"只留"隔离处置记录"。
结果：**演练里"报案"变成一句口头动作**，参演人不知道要交什么；复盘也无法回答"攻击流量特征、峰值、源 IP 清单在哪里"。

### 2.2 合规倒挂：报案被外部意见门控，而"直接报案"被判错（P0）

- S03-11 标题"根据市卫健局+网信办意见确定是否报市网安大队立案取证"，`deps=["S03-6","S03-7"]`。
- 混淆 `DSS03-itlead-11-2` 是"直接报案让网安介入"，被判为错误。
- 训练出的行为是"等两家上级回复后再决定报不报案"，与 S01 已纠正的"先行报案"相反。

### 2.3 把正确动作设为混淆（5 条，P0）

| 混淆节点 | 现标题 | 为什么是正确动作 |
|---|---|---|
| DSS03-netsec-2-1 | 用 NTOP 看带宽占用情况 | 流量型攻击核实的标准手段，比翻防火墙日志更快 |
| DSS03-netsec-10-2 | 让运营商协助封禁攻击 IP | 大流量 DDoS 的上游清洗/封禁是正规做法 |
| DSS03-itlead-7-1 | 先发初步告警，后续进展再动态更新 | 初报 + 续报是规范上报方式 |
| DSS03-itlead-11-2 | 直接报案让网安介入 | 较大事件先行报案是正确行为 |
| DSS03-itlead-3-1 | 按"收费>2 小时中断 = Ⅲ级"直接定 | 接近正确：按预案规则定级本身没问题，问题只是"只看时长不看影响范围" |

### 2.4 止损与取证的先后关系没有约束（P0）

S03-8（清洗）与 S03-14（拟新增取证）没有依赖关系，S03-10（溯源）只依赖 S03-8。
现状下参演人可以"先清洗、后溯源"，清洗一开，攻击流量样本与源 IP 分布就没了；应当"先抓包/留存清洗设备日志，再下清洗策略"。

### 2.5 内容与表单失守（P0）

`descr` 13/13 空、`short_title` 13/13 NULL；F8 绑在"报告并建议启动"节点；业务兜底（S03-9）、恢复验证（S03-12）无表单，20% 质量分无法计算。
